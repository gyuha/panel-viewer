# run — 화면에 맞추기 확대 (fit-screen-upscale)

실행일: 2026-08-05 · 방식: Dynamic Workflow 없이 직접 실행

## 슬라이스별 결과

- S1 base `.viewer-page`의 `width`/`height`를 `auto` → `100%` — ✅ 계획대로
- (추가) `.viewer-stage`의 `padding: var(--s-base)` → `0` — ⚠ 플랜에 없던 UAT 유발 변경, 플랜의 명시 요구사항과 일부 충돌

## 워크플로를 쓰지 않은 이유

CSS 속성 2개 변경. 서브에이전트 기동 비용이 작업 자체보다 크다.

## 계획 대비 실제

계획대로. 플랜이 예측한 그대로 **base 규칙 한 곳만 고쳐서 끝났고**, 새 `.fit-screen` 규칙도, 다른 파일 변경도 없었다. 변경된 줄은 `width: auto → 100%`, `height: auto → 100%` 두 줄이며 여기에 이유 주석 2줄을 덧붙였다(왜 `auto`가 아니라 `100%`인지 — 나중에 누가 "auto가 더 자연스럽다"며 되돌리는 것을 막기 위함).

플랜에서 근거를 대둔 두 가지가 실제로 성립함을 코드에서 재확인했다:
- `fit-width`(`App.css:786`)·`fit-height`(`:793`)·`fit-original`(`:800`)이 base가 설정하는 `width`·`height`·`max-width`·`max-height`·`object-fit`을 **전부** 덮어쓴다 → 이 변경은 `fit-screen`에만 도달한다.
- `click-zone`은 `position: absolute`(`:809`)라 이미지 박스 크기와 무관하다.

TS 파일은 한 줄도 바뀌지 않았다(`tsc` 통과, 테스트 60개 그린은 회귀가 없다는 뜻일 뿐 이 변경을 검증하지 않는다 — 아래 참고).

## UAT 중 추가된 변경 (플랜 밖)

UAT 도중 사용자가 **이미지와 창 사이 여백을 없애 달라**고 요청해 `.viewer-stage`의 `padding: var(--s-base)`(16px)를 `0`으로 바꿨다.

측정 근거: 당시 창 **658×1023**, 페이지 **975×1435**(4.cbz). 좌우 패딩 합 32px이 **창 폭의 5%**를 차지했다 — 작은 창에서 유독 두드러지는 값이다. (참고로 그 화면의 `contain` 배율은 `min(626/975, 947/1435)` = **0.642배로 축소**였다. 즉 사용자가 보고 있던 화면은 S1의 확대 경로가 아니라 축소 경로였고, S1 자체를 검증해주지 않는다.)

**플랜과의 충돌을 명시한다**: 플랜의 비목표에 *"고해상도 이미지의 표시 결과를 바꾸지 않는다 — 부수 효과가 아니라 요구사항이다(회귀 금지)"*라고 적었는데, 패딩 제거는 스테이지를 각 방향 32px 늘려 **모든 이미지를 약 5% 크게** 만든다. 따라서 이 변경은 그 요구사항을 부분적으로 위반한다. 별도 태스크로 쪼개지 않고 접어넣은 판단 근거는 (1) 한 줄 변경이고 (2) 직전 태스크 #17에서도 UAT가 배치 결정을 뒤집었을 때 같은 방식(접어넣고 run.md에 차이로 기록)으로 처리했으며 (3) 그 사이 창 크기가 1605×1287 → 658×1023으로 바뀌어 **"수정 전과 픽셀 동일"식 비교는 이미 불가능**해졌기 때문이다. 그래서 UAT의 고해상도 확인 항목은 "픽셀 동일"이 아니라 "잘림 없이 비율 유지로 올바르게 표시"로 읽어야 한다.

회귀 위험 확인: `seek-backdrop`은 `.viewer` 기준 `inset: 0`이라 스테이지 패딩과 무관하고, `click-zone`은 `width: 40%` 비율 기반이라 패딩 제거 후에도 같은 비율을 덮는다.

## 검증 결과

- `npx tsc --noEmit` → 0
- `npx vitest run` → 60개 통과 (기존 그대로. **이 변경을 검증하지는 않는다** — `vitest.config.ts`에 `css` 옵션이 없어 기본 `css: false`이므로 테스트 중 스타일시트가 처리되지 않고, jsdom에는 레이아웃 엔진이 없어 백분율·`object-fit` 계산이 관측 불가하다. 회귀 부재 확인용)
- `npx vite build` → 성공 (CSS 12.83 kB)
- Rust 무변경 → `cargo check` 생략

## UAT에서 반드시 볼 것 (직전 회고 교훈의 적용)

직전 태스크 회고에 *"정적 목업은 가림 면적은 보여주지만 읽기를 방해하는가는 보여주지 못한다"*고 적었다. 이번 태스크의 실질 위험이 같은 부류다 — **"폭이 꽉 찼는가"는 눈에 바로 보이지만 "1.6배 확대된 말풍선 글씨가 읽을 만한가"는 실제로 읽어봐야 안다.** 후자가 UAT의 핵심 항목이며, 여기서 "읽기 힘들다"가 나오면 그릴링에서 기각한 **확대 상한(안 b)**을 다시 꺼내야 한다. 상한을 기각한 근거는 "`원본`이 선명함을 담당한다"였는데, 그건 *작게라도 선명하면 읽힌다*는 가정에 서 있다 — 그 가정이 실사용에서 깨지는지가 이번 확인 사항이다.
