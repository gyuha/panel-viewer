# 2026-08-03 — 페이지 탐색 슬라이더 (카운터 클릭 → 하단 슬라이더)

## Plan vs actual

- **계획대로 된 것**: 슬라이스 4개 전부 착지. S1은 TDD가 제대로 작동해 red 4건을 먼저 확인하고 구현했고, 플랜이 지목한 함정(`.continuous`에 `position`이 없어 자식의 `offsetParent`가 컨테이너가 아니므로 `offsetTop`이 조용히 틀린다)은 실재했다. S3의 명령 통로는 예상대로 작았다. IntersectionObserver 되먹임 억제 장치가 필요 없다는 플랜의 예측도 맞았다 — 드래그 중 슬라이더가 로컬 값을 쓰므로 IO가 되쏘는 `onPageChange`는 무해하고 오히려 툴바 카운터를 동기화한다.

- **차이**:
  1. **플랜의 사실 오류** — "컴포넌트 테스트 인프라가 없다"는 전제가 틀렸다(아래 학습 ①). 발견 즉시 컴포넌트 테스트 10개를 추가해 TDD 범위를 넓혔다.
  2. **S4가 지시한 `ContinuousView` 휠 게이트를 만들지 않았다** — 투명 backdrop이 `.viewer` 안에서 `inset:0`으로 깔리는데 `.continuous`의 wheel 리스너는 그 컨테이너에 붙어 있고 backdrop은 **형제**라 이벤트 경로에 없다. 게이트를 넣었으면 도달 불가능한 죽은 코드가 됐다. **단 실측 미완**(아래 열린 항목).
  3. **투명 backdrop은 플랜에 없던 요소** — "바깥 클릭 닫기"를 구현하다 도입했고, 부수적으로 위 2번과 "클릭존이 게이트 대상이 아니어서 바깥 클릭이 페이지를 넘겨버리는" 문제를 함께 해결했다.
  4. **`seekOpen`을 App으로 올렸다** — `App.tsx`의 전역 핸들러가 `settingsOpen`만 보고 있어, 슬라이더 조작 중 `x`를 누르면 앱이 종료됐다. 플랜의 S4 목록엔 이 핸들러가 없었다.
  5. **게이트 소유권을 중간에 한 번 되돌렸다** — 처음엔 App이 `!settingsOpen && !seekOpen`을 계산했으나 그러면 Viewer 테스트가 허수가 된다(테스트가 그 조합을 직접 만들어 넣으므로 App이 빠뜨려도 통과). App은 `!settingsOpen`만, Viewer가 `keysLive`를 스스로 계산하도록 바꿨다.
  6. **UAT가 그릴링에서 정한 배치 결정을 뒤집었다** — 가운데 → 하단.

## Learnings

- **다음엔 다르게: "없다"는 부재 주장도 전수 확인 대상이다.**
  직전 회고의 교훈은 "결함·현황 보고 전에 `grep` 전수 조사를 먼저"였고, 그건 **개수를 셀 때** 지켰다. 그런데 이번엔 `vitest.config.ts`를 열지 않고 "컴포넌트 테스트 인프라가 없다"고 단정했다. 실제로는 `environment: "jsdom"` · `setupFiles` · `include: ["src/**/*.test.{ts,tsx}"]`(`.tsx` 명시)까지 설정돼 있었고 `@testing-library/react`도 설치돼 있었다 — 쓰인 적이 없었을 뿐이다. 그 틀린 전제 위에서 "TDD가 물 게 없다"며 범위를 좁혔으니, **잘못된 사실 하나가 태스크 설계를 바꿨다.**
  → 규칙을 넓힌다: **"X가 없다/불가능하다"를 근거로 범위를 좁히려 할 때는, 좁히기 **전에** 설정 파일·의존성·스크립트를 직접 읽어 확인한다.** 특히 "테스트할 수 없다", "인프라가 없다", "이 저장소는 안 쓴다" 류의 주장이 위험하다. 관련 사실이 `CLAUDE.md`에 있어도 그것만 믿지 않는다 — 이 저장소의 `CLAUDE.md`도 "GUI 상호작용은 기계적으로 테스트 불가"라고만 적혀 있어(E2E 얘기다) 컴포넌트 테스트 가능성을 가리고 있었다.

- **다음엔 다르게: 정적 목업은 "가림 면적"은 보여주지만 "읽기를 방해하는가"는 보여주지 못한다.**
  시각 도우미로 3안을 나란히 비교해 "가운데"를 골랐는데, 실사용 한 번에 하단(반론으로 넣었던 C안)으로 뒤집혔다. 목업이 틀린 게 아니라 **목업이 답할 수 없는 질문**이었다 — 컷을 눈으로 따라가는 동작은 정지 화면에 없다. 배치·인체공학 결정은 목업으로 후보를 좁히되, **동작 중 판단이 필요한 항목은 "먼저 붙여보고 UAT에서 확정"으로 미루는 게 맞다.** 이번엔 CSS `align-items` 한 줄이라 대가가 없었지만, 구조가 배치에 얽힌 기능이었으면 재작업이었다.

- **다음엔 다르게: 테스트를 쓸 때 "이 테스트가 없으면 무엇이 통과해버리는가"를 먼저 확인한다.**
  Viewer 게이트 테스트를 처음 쓴 형태는 허수였다(테스트가 `shortcutsEnabled={!seekOpen}`을 직접 만들어 넣어, 프로덕션 코드가 게이트를 빠뜨려도 통과). 게이트를 일부러 제거해 **해당 테스트만 실패하는지** 확인(뮤테이션)해서 잡았다. 이 확인은 30초짜리이고, 새로 쓴 테스트에는 기본으로 붙일 것.

- **프로세스 사고 둘.**
  - `cd src-tauri && cargo check`의 작업 디렉터리가 **이후 모든 명령에 남아** `ls src-tauri/target/...`이 실패하고 vite가 프로젝트 설정을 못 찾아 기본 포트(5173)로 떴다. `devUrl`은 1420이라 앱이 붙지 못했다. → 디렉터리를 옮기는 명령은 절대 경로로 대체하거나, 옮겼으면 다음 명령에서 되돌린다.
  - 백그라운드로 띄운 GUI 앱이 프로세스 그룹 정리와 함께 죽었다. `nohup … & disown`으로 분리하면 살아남는다 — macOS GUI 앱을 UAT용으로 띄울 때의 정석.
  - **UAT 미완 상태로 릴리스가 나갔다.** 사용자 지시였고 `verified:`에 공백(휠 차단·`x` 종료 차단 미실측)을 명시해 기록했으니 감춘 건 없지만, 순서상 검증이 배포에 앞서는 게 맞다.

- **확인됨 (지난 회고 교훈의 적용 결과)**: "순수 로직 분리가 TDD를 값지게 만든다"는 이번에도 맞았다. `scrollTopForPage`는 단정 4개짜리 작은 함수지만, 그 안에 `offsetTop`을 쓰면 조용히 틀리는 함정이 들어 있어 값이 실질적이었다.

## 열린 항목 (다음 루프로 넘김)

- **backdrop의 휠 차단 실측 + ADR 승급 보류.**
  *"바 열림 중 입력 차단을 컴포넌트별 게이트가 아니라 전면 backdrop 하나로 한다"*는 ADR 3조건을 모두 넘는다 — ① backdrop을 줄이거나 `pointer-events: none`을 붙이면 **조용히** 휠·클릭존이 되살아나고 어떤 테스트도 못 잡는다, ② 플랜은 게이트를 지시했는데 코드엔 없어 미래 독자가 의아해한다, ③ 명시적 게이트 대신 backdrop을 고른 실제 트레이드오프가 있다.
  **그런데 근거인 "backdrop이 휠을 막는다"가 실측되지 않았다.** 검증 안 된 주장을 영구 결정 기록에 올리는 것은 위 학습 ①을 그 자리에서 되풀이하는 일이므로 **의도적으로 보류했다.**
  다음 할 일: 설치본(v0.2.8)에서 바를 띄우고 휠을 굴려 확인 → 막히면 ADR 작성(전파 절반은 jsdom 테스트로 고정 가능, z-index 스택 절반은 실측만), 막히지 않으면 `ContinuousView` 휠 게이트 2줄 추가.

- **휠 관성 애니메이션과 스크럽의 경합** — 휠을 굴려 관성이 남은 동안(≈300~500ms) 바를 열고 즉시 드래그하면 rAF 루프가 `scrollTop`을 되돌릴 수 있다. `run.md`에 판단 근거와 함께 미해결로 기록했다(그 스크롤 루프는 과거 버그 주석이 빽빽한 자리라, 실측된 실패 없이 건드리면 회귀 위험이 이득보다 크다).

- 그릴링에서 제안했다가 만들지 않은 백로그 2건: ① 연속 모드 자리 예약 정확도(백엔드가 페이지 크기 제공 → `.cont-page`의 `min-height: 60vh` 근사 해소), ② 페이지 탐색에 재지정 가능한 단축키 부여.
