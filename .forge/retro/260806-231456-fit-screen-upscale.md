# 2026-08-06 — 한장 모드 `화면에 맞추기`의 저해상도 확대 (CSS 2줄 + 패딩 제거)

## 계획 대비 실제

- **계획대로 된 것**: S1 착지. 플랜의 진단이 추측이 아니라 **측정값**(이미지 984×739, 창 1605×1287, 스테이지 ≈1573×1211, `contain` 배율 `min(1.60, 1.64)` = 1.60배 폭 제약)이었고 예측이 그대로 맞았다. 플랜이 근거를 대둔 두 주장도 실행 시점과 회고 시점 양쪽에서 코드로 재확인됐다 — ① `fit-width`(`App.css:786`)·`fit-height`(`:793`)·`fit-original`(`:800`)이 base의 `width`·`height`·`max-width`·`max-height`·`object-fit` **5개 전부**를 덮어써서 base 변경이 `fit-screen`에만 도달한다, ② `click-zone`은 `position: absolute` + `width: 40%`라 이미지 박스·패딩과 무관하다. 별도 `.fit-screen` 규칙도, 다른 파일 변경도 필요 없었다.
  회고 중 추가 확인: `.viewer-stage`는 `PageView.tsx`만 쓰고 연속 모드는 `.continuous`/`.cont-page`/`.cont-img`라는 **별개 컨테이너**를 쓴다 → 패딩 제거가 연속 모드에 닿지 않아 플랜의 비목표("연속 모드는 건드리지 않는다")는 지켜졌다.

- **차이**:
  1. **UAT가 완료 정의가 지목한 파일을 쓰지 않았다** — 플랜은 파일명·해상도까지 못박았는데(은혼-001.cbz 984×739 → 확대 경로) UAT는 4.cbz(975×1435, 창 658×1023)로 했고 그 화면의 `contain` 배율은 **0.642배 축소**였다. 즉 **이 태스크가 고친 코드 경로가 UAT에서 아예 실행되지 않았다.** `run.md`가 이 사실을 정직하게 기록했지만, 기록했을 뿐 UAT를 다시 하지는 않았다. → 학습 ①
  2. **UAT가 플랜의 명시적 비목표를 뒤집었다** — 사용자가 UAT 중 여백 제거를 요청해 `.viewer-stage`의 `padding: var(--s-base)`(16px) → `0`. 플랜 비목표에 *"고해상도 이미지의 표시 결과를 바꾸지 않는다 — 부수 효과가 아니라 요구사항이다(회귀 금지)"*라고 적었는데, 패딩 제거는 스테이지를 각 방향 32px 늘려 **한장 모드의 모든 이미지를 약 5% 크게** 만든다. 실측 근거는 있었다(작은 창에서 좌우 32px = 폭의 5%). → 학습 ②
  3. **검증 미완 상태로 릴리스가 나갔다** — `verified: pending`인 채 `0ce5bef` 커밋 → `b6e9f1f chore: release v0.2.9`. `verified: yes`는 **다음 날 별도 세션**에서 채워졌다. → 학습 ③

## 학습

- **다음엔 다르게: 완료 정의가 특정 입력을 지목했으면 UAT는 그 입력으로 한다.**
  코드가 조건 분기를 가질 때(여기서는 `object-fit: contain`의 확대 경로 vs 축소 경로) **다른 분기를 확인한 것은 0% 검증이지 부분 검증이 아니다.** 이번엔 플랜이 파일명과 해상도까지 적어놨는데도 다른 파일로 UAT를 했고, `run.md`는 "S1 자체를 검증해주지 않는다"고 스스로 진단해놓고 그 상태로 `pending`을 굳혔다 — **진단이 행동으로 이어지지 않았다.**
  직전 회고 #17의 *"정적 목업은 가림 면적은 보여주지만 읽기를 방해하는가는 보여주지 못한다"*와 같은 부류지만 성격이 다르다: #17은 **도구의 근본 한계**(재작업 불가), 이번은 **파일 하나 잘못 연 것**(30초면 교정). 후자를 놓치는 게 더 아깝다.
  → 규칙: UAT 시작 전 "지금 열려는 입력이 플랜의 완료 정의가 지목한 그것인가"를 한 번 확인한다. 아니면 열지 말고 지목된 걸 찾는다. `run.md`에 "이 UAT는 대상을 검증하지 않는다"를 쓰게 되는 순간이 곧 **UAT를 다시 해야 한다는 신호**다.

- **다음엔 다르게: 비목표를 뒤집는 UAT 요청은 "한 줄이니까"로 접지 말고 비목표를 다시 판정한다.**
  #17에서는 UAT가 **플랜이 정한 결정**(슬라이더 배치)을 뒤집었고, 이번엔 **플랜이 근거를 대며 배제한 것**을 요구했다. 2연속이지만 후자가 무겁다 — 전자는 "플랜의 결정이 잠정적이었다"는 뜻이고, 후자는 **비목표가 UAT 앞에서 무력하다**는 뜻이다. 비목표는 그릴링에서 근거를 붙여 배제한 것인데 실사용 한 마디에 접혔다.
  `run.md`가 든 접어넣기 근거 3개 중 앞의 둘(한 줄 변경·#17 선례)은 유효하지만 **세 번째("그 사이 창 크기가 바뀌어 픽셀 동일 비교가 이미 불가능")는 논거가 아니라 결과다** — 비교가 불가능해진 사정일 뿐, 비목표를 위반해도 된다는 근거가 못 된다. 실제로 그 위반은 UAT의 판정 기준까지 바꿨다("픽셀 동일" → "잘림 없이 비율 유지").
  → 규칙: UAT 요청이 비목표를 건드리면 **접어넣기 전에 그 비목표가 왜 비목표였는지 한 줄로 다시 읽는다.** 근거가 아직 유효하면 별도 태스크로 쪼갠다. 접어넣기로 결정했으면 **UAT 기준이 바뀌었다는 사실까지** `run.md`에 쓴다(이번엔 이건 제대로 했다).

- **반복됨(2연속): 검증이 배포에 앞서야 한다.**
  #17 회고에 *"UAT 미완 상태로 릴리스가 나갔다 … 순서상 검증이 배포에 앞서는 게 맞다"*고 적었고, #18에서 또 그랬다. 두 번 다 감춘 건 없다(둘 다 `verified:`에 공백을 명시했다) — 문제는 **기록이 순서를 바꾸지 못했다**는 것이다. 회고에 적는 것만으로는 이 항목이 고쳐지지 않는다는 게 이번의 진짜 발견이다.
  → 구체적 트리거: `chore: release` 커밋을 만들려는 순간 `.forge/STATUS.md`의 `verified:`를 읽는다. `pending`이면 릴리스 전에 UAT를 끝낸다. (fg-done의 봉인 게이트는 릴리스를 막지 못한다 — 릴리스는 forge 루프 밖의 행위이기 때문.)

- **확인됨: 측정값 기반 진단은 값을 냈다.**
  플랜이 배율을 실제로 계산해뒀기 때문에 "확대가 왜 안 일어나는가"(`max-*`는 축소만, `width/height: auto`는 자연 크기 유지)와 "고치면 몇 배가 되는가"(1.60배)가 처음부터 명확했고, 그 덕에 `확대 상한`을 둘지 말지를 그릴링 단계에서 판정할 수 있었다. 상한 없이 가기로 한 근거("선명함은 `원본`이 담당한다")는 UAT에서 "읽을 만하다"로 확인되어 긴장이 해소됐다 — 이 판정이 뒤집혔으면 상한을 다시 꺼내야 했다.

- **주석에 "왜 이 값인가"를 남긴 게 맞았다.**
  `width: 100%`에 *"auto면 뷰어보다 작은 이미지가 자연 크기로 남아 확대되지 않는다"*를, `padding: 0`에 *"여백이 필요하면 이 값만 되살리면 된다"*를 붙였다. 둘 다 나중에 "auto가 더 자연스럽다" / "여백이 있어야 보기 좋다"로 되돌릴 유혹이 실재하는 자리다. 후자의 주석은 ADR 승급을 불필요하게 만든 실질 근거이기도 했다(되돌리는 법이 코드에 적혀 있으면 되돌리기 쉬운 결정이다).

## 열린 항목 (다음 루프로 넘김)

- **연속 모드 `.cont-img`의 `max-width: 900px`** — 플랜이 비목표로 명시하고 별도 태스크로 남긴 항목. **이번 태스크로 비대칭이 커졌다**: 한장 모드는 이제 창 끝까지 채우는데(패딩 0 + 확대) 연속 모드는 창 폭과 무관하게 900px 상한이다. 최초 커밋 `f7bf594`부터 있었고 근거 기록이 없다(`git log -S`로 확인). 걷어내면 저해상도 파일만이 아니라 **지금 잘 보던 모든 파일의 읽기 폭이 바뀐다** — 그래서 태스크 이름은 "900px 제거"가 아니라 **"연속 모드의 읽기 폭을 어떻게 정할지"**가 맞다.
- **#17에서 넘어온 미결(여전히 열려 있음)**:
  - backdrop의 휠 차단 실측 + ADR 승급 보류 — v0.2.9 설치본이 있으니 지금 실측 가능하다. 막히면 ADR 작성, 안 막히면 `ContinuousView` 휠 게이트 2줄 추가.
  - 휠 관성 애니메이션과 스크럽의 경합(≈300~500ms).
  - 백로그 2건: 연속 모드 자리 예약 정확도(`.cont-page`의 `min-height: 60vh` 근사 해소), 페이지 탐색에 재지정 가능한 단축키.

## 문서 갱신

- **CONTEXT.md 승급: 없음.** `이미지 맞춤` 용어는 이 태스크의 fg-ask 그릴링에서 이미 추가됐고 *"맞추기는 축소만이 아니라 확대도 포함한다"*까지 명시되어 있다(`CONTEXT.md`). 이번 실행에서 바뀐 것은 패딩(구현 세부)뿐 — 용어집에 픽셀 경계를 적으면 오염이다(#17이 슬라이더 배치를 두고 내린 것과 같은 판단).
- **ADR 추가: 없음.** 세 후보 모두 3조건 중 "되돌리기 어렵다"에서 탈락 — 패딩 0은 한 줄이고 주석에 되살리는 법까지 적혀 있으며, 확대 상한 없음도 CSS 한 줄이고 근거는 아카이브되는 플랜에 남는다. "UAT 밖 요청을 어떻게 처리할지"는 이 프로젝트의 ADR 소속이 아니다 — 여기 ADR 3건은 전부 기술 결정(unrar 크레이트·프리페치 캐시·mousedown 매핑)이고, 프로세스 규칙은 이 회고 로그가 받는다.
