# 아카이브를 열 때 전체 페이지를 백그라운드 스레드로 인메모리 캐시에 미리 추출한다

지금은 페이지 바이트를 `pvpage://` 요청마다 추출하고(아카이브 재오픈 + `detect_kind`), 특히 RAR는 순차 포맷이라 N번째 페이지를 읽으려 매번 처음부터 헤더를 스캔한다 — 페이지당 O(N), 전체로 O(N²)이고, 네트워크 드라이브에서는 페이지마다 왕복이 생겨 스크롤이 끊긴다. 그래서 **아카이브를 열면 백그라운드 스레드가 아카이브를 한 번 순차로 훑어 모든 페이지의 인코딩 바이트를 인메모리 캐시(`index → bytes`)에 채우고**, 프로토콜 핸들러는 캐시 우선 조회 후 미스에만 온디맨드로 폴백한다. 순차 1패스로 RAR가 O(N²)→O(N)이 되고, 캐시 히트 이후로는 네트워크 왕복이 사라진다.

## Considered Options

- **슬라이딩 윈도우(현재 페이지 ±N만 캐시)** — 메모리는 적게 쓰지만 RAR에서 여전히 랜덤 액세스(페이지당 처음부터 스캔)라 근본 병목이 남고, 빠른 스크롤이 윈도우를 앞지른다. 기각.
- **디스크 임시 캐시** — RAM은 아끼지만 캐시 디렉터리 정리·수명 관리 부담이 크고, 인코딩 바이트는 어차피 아카이브 크기 수준이라 RAM으로 충분. 기각.

## Consequences

- 현재 아카이브 하나의 **인코딩 이미지 바이트 전체가 RAM에 상주**한다(디코딩 픽셀이 아니라 jpg/png 원본 바이트 ≈ 아카이브 크기). 앱은 한 번에 아카이브 하나만 열므로 상주분은 항상 하나뿐이고, 파일 전환 시 이전 캐시는 해제한다. 현재 대상 파일 규모(수십~수백 MB)에서는 상한을 두지 않는다.
- 백그라운드 스레드와 프로토콜 핸들러가 캐시를 공유하므로 **세대(generation) id로 무효화**한다 — 파일 전환마다 id를 올리고 캐시를 비우며, 옛 스레드는 자기 세대가 낡았음을 감지하면 중단해 새 아카이브 캐시를 오염시키지 않는다(프런트의 캐시버스트 토큰과 같은 원리).
