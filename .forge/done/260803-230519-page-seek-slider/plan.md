# 페이지 탐색 슬라이더 — 카운터를 눌러 임의 페이지로 건너뛰기

## 목표 / 비목표

- **목표**: 뷰어 툴바 오른쪽의 현재 위치 표시(`62 / 97`)를 누르면 뷰어 영역 가운데에 슬림한 반투명 바가 뜨고, 그 안의 슬라이더를 끄는 동안 **뒤 화면이 실시간으로 따라 이동**한다. 한장·연속 두 모드 모두에서 동작한다.
- **비목표**:
  - **단축키 부여 안 함.** 카운터 클릭(및 그 버튼에 Tab 포커스 후 Enter/Space)만이 여는 방법이다. `keymap.ts`의 `ACTIONS`·`STANDARD_KEYS`·`DEFAULT_CUSTOM`과 설정 모달의 단축키 표는 **건드리지 않는다**. → 원하면 별도 태스크.
  - **취소·되돌리기 없음.** 스크럽으로 옮긴 위치가 그대로 읽던 위치가 된다. 이 앱엔 애초에 읽던 위치 되돌리기가 없고, 이 모달에만 넣으면 일관성이 깨진다.
  - **연속 모드의 레이아웃 밀림은 고치지 않는다.** `App.css:678`의 `.cont-page { min-height: 60vh }`는 실제 페이지 높이(폭 900px 기준 통상 1200px+)의 절반쯤이라, 먼 페이지로 점프하면 이미지가 로드되며 위치가 밀린다. 이건 **기존 결함**이며(지금도 `ContinuousView.tsx:127`의 마운트 시 복원에서 발생) 근본 해결은 백엔드가 페이지별 크기를 실어 보내야 하는 별개 관심사다. → 원하면 별도 태스크.
  - 썸네일 미리보기, 페이지 번호 직접 입력, 처음/±1/마지막 버튼 없음 — 앞의 셋은 요청 범위 밖이고, 마지막은 `Home`/`End`·`←`/`→`·한장 모드 좌우 클릭 존의 재탕이다.
  - `pageCount === 0` 방어 없음. `src-tauri/src/lib.rs:55`가 이미지 0장 아카이브를 에러로 거부하므로 뷰어에 도달 불가능한 상태다.

## 근거 문서

- **용어집**: `.forge/CONTEXT.md`의 **페이지 탐색**(이번 그릴링에서 신규 추가) · **동작** · **보기 모드** · **읽던 위치**. 페이지 탐색은 `동작`이 **아니다**(단축키 없음).
- **관련 ADR**: 없음. 되돌리기 어려운 결정이 없어 ADR을 만들지 않았다 — 슬라이더·실시간 스크럽·바 위치 모두 나중에 바꾸는 비용이 작다.
  참고만 할 것: `.forge/adr/260721-003136-open-prefetch-all-pages-cache.md` — 아카이브를 열면 전체 페이지 바이트가 인메모리 캐시에 미리 채워지므로, 스크럽이 스치는 중간 페이지의 비용은 **웹뷰 디코드뿐**이고 디스크·압축 해제 왕복은 없다. 실시간 스크럽이 성립하는 근거.
- **완료 정의(Definition of Done)**: 한장·연속 두 모드에서 카운터를 눌러 바를 띄우고, 슬라이더를 끄는 동안 화면이 따라 움직이며, Esc로 바만 닫히고(파일은 열린 채) 이동한 페이지가 유지된다. 바가 열려 있는 동안 화살표 키가 페이지를 **두 번** 넘기지 않는다.

## 작업 슬라이스

- [ ] **S1. `scrollTopForPage` 순수 함수 (test-first)** — `src/lib/nav.ts`에 컨테이너의 현재 `scrollTop`과 컨테이너·대상 페이지의 뷰포트 상단 좌표로부터 새 `scrollTop`을 구하는 순수 함수를 추가한다.
  **왜 이게 유일한 TDD 대상인가**: `.continuous`에는 `position` 지정이 없어(`App.css:651`) `.cont-page`의 `offsetParent`가 이 컨테이너가 **아니다.** 따라서 흔히 쓰는 `container.scrollTop = pageEl.offsetTop`은 **조용히 틀린 값**을 낸다. 올바른 식은 `curScrollTop + (pageTop - containerTop)`이고, 이건 DOM 없이 산술로 검증된다.
  — 완료 기준: `npx vitest run src/lib/nav.test.ts`가 새 단정(아래로 스크롤 / 위로 스크롤 / 이미 제자리 → 0 이동)을 포함해 전부 통과.

- [ ] **S2. 슬라이더 바 컴포넌트 + 카운터 버튼화 (한장 모드)** — `src/components/PageSeekBar.tsx`를 새로 만들고 `Viewer`에 로컬 열림 상태를 둔다. `Viewer.tsx:159`의 `<span className="viewer-count">`를 `<button>`으로 바꿔 토글로 쓴다.
  - 바 내용물은 **슬라이더 + `{page+1} / {pageCount}`뿐**. `<input type="range" min=0 max={pageCount-1}>`로 0-based 인덱스를 직접 다루고, 표시만 +1 한다.
  - 드래그 중에는 슬라이더가 **로컬 값**을 쓰고 `onChange`마다 `onPageChange`를 호출한다(실시간 스크럽). 드래그 중이 아닐 때는 `page` prop을 따라간다 — 그래야 휠·키로 넘긴 위치가 바에 반영된다.
  - 스타일: 딤 배경 **없음**. `.viewer` 기준 `position: absolute`로 가운데(툴바 아래 영역), 반투명 배경 + `backdrop-filter`. **`.viewer`에 `position: relative`를 추가해야 한다**(`App.css:568`에 현재 없음).
  - 닫기: Esc · 바깥 클릭 · 카운터 재클릭. **Esc는 반드시 `e.stopPropagation()`** — 안 하면 `Viewer.tsx:71`의 Esc가 `onClose()`를 타고 `App.tsx:374`에서 **읽던 파일이 통째로 닫힌다**. `SettingsModal.tsx:102`가 같은 이유로 쓰는 방어다.
  - 드래그를 놓아도 **바는 닫히지 않는다**(미세 조정을 위해).
  — 완료 기준: `task dev`에서 한장 모드로 파일을 열고 카운터를 클릭 → 바가 뜬다. 슬라이더를 끝에서 끝까지 끌면 뒤 이미지가 끄는 내내 바뀐다. Esc를 누르면 바만 닫히고 파일은 열려 있으며, 이동한 페이지가 유지된다.

- [ ] **S3. 연속 모드 스크롤 통로** — `ContinuousView`가 밖에서 "N번 페이지로 스크롤"을 받을 수 있게 한다(`useImperativeHandle`로 `scrollToPage(i)` 노출 등). 내부는 S1의 `scrollTopForPage`와 `getBoundingClientRect()`로 계산해 `containerRef.current.scrollTop`에 대입한다. (depends: S1, S2)
  - `ContinuousView.tsx:36`의 `initialPage`는 마운트 시점 값 고정이라 `page` prop 변경만으로는 스크롤되지 않는다 — 그래서 통로가 필요하다.
  - `ContinuousView.tsx:160`의 IntersectionObserver 되먹임을 **막을 필요는 없다**: 드래그 중 슬라이더는 로컬 값을 쓰므로 IO가 되쏘는 `onPageChange`는 무해하고, 오히려 툴바 카운터를 자동 동기화한다. 마운트용 `suppress` ref 같은 억제 장치를 새로 만들지 말 것.
  — 완료 기준: `task dev`에서 연속 모드로 97쪽짜리 파일을 열고 슬라이더를 끌면 페이지 더미가 끄는 대로 스크롤된다. (먼 페이지로 점프했을 때 이미지 로드에 따라 위치가 다소 밀리는 것은 **비목표**이며 결함으로 세지 않는다 — 다만 실제로 얼마나 밀리는지 관찰해 run 노트에 적을 것. WebKit은 `overflow-anchor`를 지원하지 않는 것으로 보이므로 Chrome보다 심할 수 있다.)

- [ ] **S4. 바가 열린 동안 기존 키·휠 전면 차단(대칭)** — `Viewer`에서 `shortcutsEnabled && !seekOpen`을 계산해 자신의 키·마우스 핸들러와 `PageView`·`ContinuousView`에 내려보낸다. (depends: S2)
  - **왜 필수인가**: `PageView.tsx:89`와 `Viewer.tsx:90`의 `keydown` 리스너는 `window`에 붙어 있고 **포커스를 확인하지 않는다.** 차단하지 않으면 `→` 한 번에 슬라이더가 1칸 움직이고 `nextPage()`도 함께 불려 **두 페이지가 넘어간다.**
  - **`ContinuousView`의 휠 핸들러에도 게이트를 신설해야 한다.** 지금 이 핸들러는 `shortcutsEnabled`의 통제를 전혀 안 받는다(`ContinuousView.tsx:44`, 마운트 시 1회 구독). 그냥 두면 "한장 모드에선 휠이 죽는데 연속 모드에선 살아 있는" 비대칭이 생긴다. 최신 props를 읽는 `cb` ref 패턴이 이미 있으므로(`ContinuousView.tsx:40`) 거기에 얹으면 된다.
  — 완료 기준: 바가 열린 상태에서 `→`를 한 번 누르면 페이지가 **정확히 1장** 넘어간다(슬라이더만 동작). 한장·연속 두 모드 모두에서 바가 열린 동안 휠이 페이지/스크롤을 움직이지 않는다. 바를 닫으면 둘 다 원래대로 돌아온다.

## 수동 검증(UAT) 체크리스트

이 태스크의 위험은 전부 **GUI 배선**이고 Vitest 사각지대다(이 저장소엔 컴포넌트 테스트 인프라가 없다 — `lib/`의 순수 로직만 테스트한다). 회고 두 편이 같은 교훈을 남겼다: *"GUI 배선 슬라이스는 빌드·단위테스트로 안 잡힌다. 완료 선언 전 런타임 스모크를 반드시 넣을 것."* `task dev`로 아래를 직접 확인한다.

1. 한장 모드: 카운터 클릭 → 바 표시 → 드래그 중 이미지가 실시간으로 바뀜
2. 연속 모드: 같은 조작으로 페이지 더미가 실시간 스크롤
3. 트랙의 빈 곳을 클릭 → 그 위치로 점프
4. 바가 열린 채 `→` 1회 → 정확히 1장 (이중 처리 없음)
5. 바가 열린 채 휠 → 두 모드 모두 무반응
6. Esc → 바만 닫힘, **파일은 열린 채**, 페이지 유지
7. 바깥 클릭 / 카운터 재클릭 → 닫힘
8. 파일을 바꾼 뒤 다시 열기 → 슬라이더 범위가 새 `pageCount`를 따름
9. 바를 열어둔 채 앱을 껐다 켜기 → 스크럽으로 옮긴 페이지가 읽던 위치로 복원됨
