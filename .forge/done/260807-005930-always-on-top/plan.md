# 항상 위 토글 — 단축키 + 툴바/빈 화면 버튼 + 상태 영속

## 목표 / 비목표

- **목표**: 창을 다른 창 위에 머물게 하는 **토글형 동작** `toggleAlwaysOnTop`을 추가한다. 커스텀 키(기본 `t`)로 **파일이 열려 있지 않아도** 동작하고, Viewer 툴바와 빈 화면 양쪽에 켜짐 상태가 보이는 버튼이 있으며, 상태는 앱을 다시 열어도 유지된다.

- **비목표**:
  - **전체화면 앱 위로는 올리지 않는다.** 그릴링에서 목적지를 "일반 창 위"로 확정했다. 전체화면 앱 위로 띄우려면 `NSWindowLevel`을 직접 조작해야 하고 이는 Tauri API 밖이라 **가능한지부터 실측**이 앞서야 한다 — 이 프로젝트 회고가 2연속으로 지적한 "실측 안 된 주장을 근거로 삼지 말라"에 걸린다. 나중에 넓히는 것은 가산적이라 지금 막을 이유가 없다.
  - **FilePanel에는 버튼을 넣지 않는다.** `togglePanel`이 FilePanel 안에 버튼을 가진 이유는 **자기 자신을 닫는 버튼**(자기 참조)이기 때문이다. 항상 위는 파일 목록 맥락과 무관해서 거기 있으면 맥락 밖에 랩는다.
  - **설정 모달에 "항상 위를 기억할지" 옵션을 추가하지 않는다.** 지금 답이 정해진 것을 사용자가 고를 설정으로 밀어놓는 과입이다. (키 재지정은 기존 표에 자동으로 나타난다 — 아래 진단 참고.)
  - **`window_size` 영속과의 상호작용을 바꾸지 않는다.** 항상 위로 창을 작게 줄이면 그 크기가 저장되어 다음 실행에도 작게 뜬다 — 기존 동작이며 그대로 둔다.
  - **작은 창 읽기 모드로 확장하지 않는다** (창 크기 프리셋·툴바 축소·창 토대 토글 등). 별도 태스크 후보.
  - **macOS 외 플랫폼은 검증하지 않는다** (`CLAUDE.md`의 macOS-first 방침).

## 근거 문서

- **용어집**: `.forge/CONTEXT.md`의 **동작** — **이번 그릴링에서 정정했다.** 기존 정의가 *"보기 모드 전환은 왕복 토글이 아니라 목표 모드를 직접 지정"*이라 못박아 토글을 배제하는 것처럼 읽혔으나, `파일 패널 토글`은 이미 토글이었다. 즉 **용어집이 코드보다 좁았다**(단축키 회고 `2026-07-18`의 교훈 *"용어집이 코드와 어긋날 수 있다"*와 같은 부류). 이제 "직접 지정형(보기 모드) vs 토글형(파일 패널·항상 위)"을 명시하고 열거에 `항상 위 토글`(`t`)을 넣었다. 관련 용어: **단축키**.
- **관련 ADR**: 없음. `항상 위`를 독립 용어로도 넣지 않았다 — 창 관리자의 일반 개념이고, "일반 창까지"라는 범위는 용어의 의미가 아니라 비목표다. ADR도 3조건 중 **"되돌리기 어렵다"에서 탈락**한다(범위를 넓히는 것은 가산적, 되돌리는 것은 필드/커맨드 제거).
- **완료 정의**: `t` 키가 파일이 열려 있을 때와 빈 화면 양쪽에서 항상 위를 켜고 끄며, 툴바·빈 화면의 버튼이 현재 상태를 `active`로 보여주고, 앱을 완전히 종료한 뒤 다시 열어도 마지막 상태가 유지된다. 구버전 `state.json`(필드 없음)은 꺼진 상태로 로드된다.

## 진단 (코드 근거 — 추측 아님)

전부 확인된 자리이고, 새로 설계할 것이 없다:

| 필요한 것 | 이미 있는 자리 |
| --- | --- |
| 전역 키 핸들러 | `App.tsx:186-206` — `settingsOpen \|\| seekOpen` 게이트 후 수식 키 없는 단일 키로 `quitApp`→`togglePanel` 검사. **세 번째 분기로 붙는다** |
| Rust에서 창 조작 | `lib.rs:316-330` — `app.get_webview_window("main")` → `win.set_size(...)`. `set_always_on_top(bool)`도 같은 경로 |
| capability 권한 | **불필요.** 프런트가 쓰는 창 API는 읽기·이벤트뿐(`onResized`·`scaleFactor`, `App.tsx:301-307`)이고 창 **변경은 Rust가 한다**는 패턴이 확립돼 있다(`App.tsx:299`의 주석 *"복원은 백엔드 setup()이 담당"*). `capabilities/default.json`은 건드리지 않는다 |
| 영속 커맨드 | `save_window_size`(`lib.rs:143-148`) — `store lock → 필드 갱신 → state::save` 3줄 |
| 설정 모달 키 표 | `SettingsModal.tsx:224`가 `{ACTIONS.map(...)}` — **새 동작이 자동으로 나타난다. 슬라이스 불필요** |
| 툴바 오른쪽 끝 | `Viewer.tsx:181`의 `viewer-count`(`3 / 45`). 그 뒤에 붙인다 |
| 빈 화면 버튼 선례 | `App.tsx:386-395`의 `panel-show-btn`(☰) — 패널 숨김 시만 렌더. 그 옆에 나란히 |
| `active` 표시 선례 | `viewer-count`의 `${seekOpen ? "active" : ""}`, `mode-btn`의 동일 패턴 |

**영속이 만드는 위험과 그 완화**: 항상 위는 이 앱에서 **앱 밖에 영향을 주는 유일한 영속 상태**다(나머지 8개 필드는 전부 앱 내부). `open_last_file`이 꺼져 있으면 시작 시 빈 화면이고 **Viewer는 `{info ? ... }`로 조건 렌더**(`App.tsx:347`)라 툴바가 없다 → 켜짐 표시가 어디에도 없으면 "왜 다른 창이 안 올라오지?"의 원인을 짚을 수 없다. **빈 화면에도 버튼을 두는 것(S4)이 이 위험의 완화책이며, 그래서 S4는 편의 기능이 아니라 요구사항이다.**

**제가 정한 두 가지 (근거와 함께 — 바꾸기 쉽다)**:
- **기본 커스텀 키 `t`** — "top"의 머리글자. 현재 사용 중인 키는 `.` `,` `1` `2` `/` `x`와 표준키(`→` `←` Space PageUp/Down Home End)뿐이라 충돌 없다. 충돌 검사(`findConflict`)가 `ACTIONS` 전체를 훑으므로 예약도 자동이다.
- **버튼 문자 `📌`** — 의미가 가장 직접적이다. 다른 버튼이 기하 문자(`☰` `<` `>`)라 톤은 어긋나지만, 알아보는 쪽이 우선이다. **UAT에서 확정할 항목** — 직전 회고의 교훈(*"동작 중 판단이 필요한 항목은 먼저 붙여보고 UAT에서 확정"*)을 그대로 적용한다.

## 검증 메모

**테스트가 잡는 것**: S1의 키맵 데이터(3-테스트 세트), S2의 serde 기본값·왕복·하위호환, S4의 버튼 렌더·콜백 호출.

**테스트가 잡지 못하는 것 — 여기가 UAT의 몫이다**: 버튼/키 → Rust 커맨드 → **실제 창이 다른 창 위로 올라가는가**. 단축키 회고(`2026-07-18`)가 명시했다 — *"GUI 배선 슬라이스는 빌드·단위테스트로 안 잡힌다… 완료 선언 전에 런타임 dispatch/auto-drive 스모크를 반드시 넣을 것."* jsdom에는 창 개념이 없고 `cargo test`는 창을 띄우지 않는다.

**직전 회고들의 교훈을 이 태스크에 적용**:
- **새로 쓴 테스트는 뮤테이션 확인을 붙인다** (#17 교훈). 특히 S1의 ②("resolve가 반환하지 않는다")는 `actionsFor()`에 일부러 넣어 **그 테스트만 실패하는지** 확인한다. 30초짜리다.
- **UAT는 완료 정의가 지목한 조건으로 한다** (#18 교훈 — 완료 정의가 파일을 지목했는데 다른 파일로 UAT해서 고친 코드 경로가 실행조차 안 된 사례). 이번 UAT의 지목 조건은 **① 파일 열림 상태, ② 빈 화면 상태 둘 다** 확인하는 것이다. 한쪽만 보면 전역 동작이 검증되지 않는다.
- **릴리스는 검증 뒤에 한다** (#17·#18 2연속 반복). `chore: release` 커밋을 만들기 전에 `.forge/STATUS.md`의 `verified:`를 읽는다.

**UAT 항목**: ① 파일 열고 `t` → 다른 앱 창 위로 올라오는가, 툴바 버튼이 `active`인가. ② 파일 닫고(빈 화면) `t` → 동작하는가, 빈 화면 버튼이 `active`인가. ③ 앱 완전 종료 후 재실행 → 상태가 유지되는가. ④ 설정 모달·페이지 탐색 바 열림 중 `t` → 발동하지 않는가. ⑤ 설정에서 `t`를 다른 키로 재지정 → 동작하는가, 충돌 거부가 되는가. ⑥ **`📌` 문자가 툴바에서 알아볼 만한가** (바꿀지 확정).
