# run — 항상 위 토글 (always-on-top)

실행일: 2026-08-07 · 방식: Dynamic Workflow 없이 직접 실행 · TDD: on

## 슬라이스별 결과

- S1 `keymap.ts`에 `toggleAlwaysOnTop` 추가(5곳) + 테스트 우선 — ✅ 계획대로 (테스트는 3개 대신 5개)

## 워크플로를 쓰지 않은 이유

슬라이스 4개가 거의 전부 직렬 의존(S3←S1+S2, S4←S3)이고 병렬 가능한 건 S1‖S2 한 쌍뿐이다. 총 8개 파일의 작은 편집이라 서브에이전트 기동 비용이 작업 자체보다 크다.

## 계획 대비 실제

플랜의 진단이 전부 성립했다. **새로 설계한 것이 하나도 없다** — 플랜이 지목한 자리가 전부 그 자리에 있었다:

- 전역 키 핸들러(`App.tsx`)에 세 번째 분기로 그대로 붙었다.
- `set_always_on_top` 커맨드는 `save_window_size`의 3줄 패턴 + `quit_app`의 `AppHandle` 주입을 합친 형태로 끝났다. `Manager`는 이미 임포트돼 있었다.
- `setup()` 복원은 `saved_size`가 쓰는 "`data`가 move되기 전에 값 복사" 방식을 그대로 따랐다(플랜이 미리 지목해둔 덕에 빌림 검사와 싸우지 않았다).
- **capability 권한 추가 없음** — 확인한 대로 창 변경을 Rust가 맡으니 `capabilities/default.json`은 손대지 않았다.
- **`SettingsModal`은 코드 변경 0줄** — `ACTIONS.map`(`SettingsModal.tsx:224`)이라 새 동작이 키 설정표에 자동으로 나타난다. 플랜이 이걸 미리 확인해 슬라이스 하나를 없앤 것이 맞았다.

플랜에 없던 위험 두 개를 **정적으로 확인해 해소**했다(둘 다 코드 변경 불필요):
- **툴바 레이아웃**: `.viewer-bar`가 `gap`을 둔 flex이고 `.viewer-title`이 `flex: 1 1 auto`로 공간을 흡수하므로, 공유 규칙에서 `flex: 0 0 auto`를 받는 새 버튼은 오른쪽 끝에 앉는다.
- **`t` 오발동**: 텍스트 입력은 3곳(`PageSeekBar:48`, `SettingsModal:165,176`)뿐이고 전부 기존 `if (settingsOpen || seekOpen) return;` 게이트 뒤에 있다. `x`(앱 종료)가 지금까지 안전했던 것과 같은 이유로 새 노출이 없다.

## 차이

1. **테스트 개수가 플랜보다 많다.** S1은 3개가 아니라 5개(표준키 없음·라벨을 별도 테스트로 분리 — `보기 모드 전환` 블록의 스타일에 맞췄다), S4는 1개가 아니라 3개(클릭 콜백·꺼짐 표시 없음·켜짐 표시 붙음). 범위 변화는 없고 같은 완료 기준을 더 촘촘히 덮는다.

2. **`resolve` 회귀 방어 테스트는 red→green 신호를 주지 않는다.** 구현 전에도 통과한다(`t`가 어디에도 매핑돼 있지 않으니 `resolve`가 당연히 null). 즉 TDD의 구동력이 아니라 **순수 회귀 방어**다. 플랜이 요구한 뮤테이션 확인(`actionsFor()`에 일부러 넣기)을 실제로 돌려 **정확히 그 1개만 실패**하는 것을 확인했다 — 허수가 아님이 증명됐다. 다른 4개는 정상적으로 red→green이었다.

3. **React 세터를 `setAlwaysOnTopState`로 명명했다.** `api.ts`의 함수명은 Rust 커맨드(`set_always_on_top`)를 미러링해 `setAlwaysOnTop`으로 뒀는데, `App.tsx`에서 `const [alwaysOnTop, setAlwaysOnTop] = useState()`를 쓰면 **함수 스코프가 모듈 임포트를 섀도잉해 api 호출이 조용히 사라진다**(창에 적용도 저장도 안 되고 에러도 안 난다). 실재하는 버그라 세터 쪽 이름을 양보했고, 이유를 코드 주석에 남겼다.

4. **전역 키 핸들러의 `togglePanel` 분기에 `return;`을 추가했다.** 내 분기가 붙어 더 이상 마지막이 아니게 됐으므로 `quitApp` 분기와 같은 조기 반환 구조로 맞췄다. `findConflict`가 키 중복을 막으니 동작은 동일하다.

5. **빈 화면 버튼을 좌상단(`panel-show-btn` 옆)이 아니라 우상단에 뒀다.** 플랜은 "`panel-show-btn` 옆"이라 적었지만 그 버튼은 **패널이 숨겨져 있을 때만 렌더**된다 — 있을 때는 겹치고, 없을 때는 좌상단에 홀로 떠 어색하다. 우상단은 조건과 무관하게 항상 비어 있어 충돌 여지가 없다. `.always-on-top-btn.floating`으로 분리했다.

6. **켜짐 표시를 브랜드색으로 정했다**(플랜이 정하지 않은 세부). `viewer-count.active`처럼 `--surface-strong`을 쓰면 **hover와 구분되지 않아** 지속 상태인지 마우스가 올라간 것인지 알 수 없다. `.file-row.active`·`.hist-row.active`가 쓰는 `background: var(--primary); color: var(--on-primary)` 관례를 따랐다.

7. **UAT 후 아이콘과 켜짐 표현을 두 번에 걸쳐 교체했다 (사용자 요청).** 최종 상태는 이렇다:
   - **이모지 → 단색 SVG 핀.** 1차로 직접 그린 핀을, 2차로 사용자가 지정한 **svgrepo `pin-01`** 로 교체했다(`src/components/AlwaysOnTopIcon.tsx` 신규). 이모지를 버린 것은 취향 외에 **실제 결함** 때문이기도 하다 — `.active`가 `color`를 지정해도 **이모지는 CSS `color`를 무시**하므로(Apple Color Emoji가 자기 색을 쓴다) 켜짐 상태의 색 지정이 아예 무의미했다. SVG는 `stroke: currentColor`로 버튼 색을 따르고, 원본의 하드코딩된 `#000000`은 크림 배경에 너무 검어서 걷어냈다.
   - **원본 path를 둘로 쪼갰다.** `pin-01`은 머리와 바늘이 한 `path`(`M12 15L12 22` + 머리 subpath)였는데, 켜짐일 때 바늘만 감추고 머리를 내리려면 따로 움직여야 해서 `.pin-needle`/`.pin-head` 두 path로 분리했다. **원본 에셋을 손대야 했던 유일한 지점**이다.
   - **켜짐을 배경색 없이 모양만으로 보인다.** 브랜드 주황(1차) → 회색(2차) → **배경 제거**(최종). `.active`에서 바늘을 `display: none`하고 머리를 바늘 길이(7 유저 단위)만큼 `translateY` — "핀을 눌러 박은" 모양이다. 7을 고른 근거: 실루엣 아래끝이 바늘 끝이 있던 `y=22`에 그대로 남아 버튼 안에서 아이콘이 들썩이지 않는다.
   - **트랜지션은 넣지 않았다.** `App.css` 900여 줄에 `transition`이 **하나도 없다** — 의도된 관례로 보고 즉시 전환으로 맞췄다.
   - hover 배경(`--surface-strong`)은 남겼다 — `panel-toggle-btn`·`panel-show-btn`과 공유하는 규칙이라 이것까지 걷으면 형제 버튼들과 어긋난다.
   - SVG 경로를 툴바·빈 화면 두 곳에 복붙하지 않기 위해 아이콘만 작은 컴포넌트로 뺐다. 버튼 마크업 자체는 기존처럼 두 곳에 그대로 두었다 — 구조 리팩터는 요청 범위 밖이다.
   - **컴포넌트 테스트 3개는 세 번의 교체 동안 한 줄도 손대지 않았다.** 버튼을 `aria-label`("항상 위")로 찾기 때문에 글리프·SVG 교체에 영향받지 않았다 — 우연이 아니라 접근성 라벨로 조회한 덕이다. 외형을 세 번 바꾸는 동안 회귀 확인이 공짜였다.

## 프로세스 사고 — 회고가 경고한 함정에 걸렸다

`cd src-tauri && cargo test`의 작업 디렉터리가 남아 이어진 `npx vite build`가 `Could not resolve entry module "index.html"`로 실패했다. **`2026-07-18` 회고가 정확히 이 함정을 기록했고**(*"디렉터리를 옮기는 명령은 절대 경로로 대체하거나, 옮겼으면 다음 명령에서 되돌린다"*), 나는 이 세션에서 그 교훈을 **소리 내어 언급한 직후에 그대로 밟았다.** 즉시 알아채고 루트에서 다시 돌려 성공했지만, 회고에 적는 것만으로는 이 항목이 고쳐지지 않는다는 증거가 하나 더 쌓였다(같은 구조의 지적이 `verified` 순서에서도 2연속이었다).

## UAT에서 반드시 볼 것

**테스트가 덮은 범위와 안 덮은 범위가 슬라이스 경계로 갈린다.** S1·S2(순수 로직·serde)는 테스트가 끝냈고, **S3·S4의 완료 기준은 런타임 조건이라 기계적으로 확인되지 않았다** — `2026-07-18` 회고의 *"GUI 배선 슬라이스는 빌드·단위테스트로 안 잡힌다"*가 그대로 적용된다. jsdom에 창 개념이 없고 `cargo test`는 창을 띄우지 않는다. 툴바 버튼은 컴포넌트 테스트 3개가 있지만 **빈 화면 버튼은 테스트가 없다**(`App.test.tsx`가 없다).

`#18` 회고의 교훈(완료 정의가 지목한 조건으로 UAT할 것)을 적용하면, 이번에 지목된 조건은 **파일 열림 상태와 빈 화면 상태 둘 다**다. 한쪽만 보면 "전역 동작"이라는 핵심이 검증되지 않는다.

그리고 `📌` 문자는 **실제 툴바에 놓인 것을 봐야** 판정된다(#17 교훈: 배치·외형은 붙여보고 UAT에서 확정).
