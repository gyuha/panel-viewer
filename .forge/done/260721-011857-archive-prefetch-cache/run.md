# run — 아카이브 페이지 백그라운드 프리페치 + 인메모리 캐시

## 실행 방식
- **Dynamic Workflow 대신 직접 실행.** 백엔드(Rust) 한정, 슬라이스가 순차 의존(S1→S2→S3)이라 병렬화 여지가 거의 없어 다수 서브에이전트가 과함(fg-run "작은 작업은 직접 처리" 원칙).

## 계획대로 된 것
- **S1** — 세션과 분리된 페이지 바이트 캐시 도입, `pvpage://` 프로토콜 핸들러를 캐시 우선 → 미스 시 온디맨드 `read_page` 폴백으로 변경.
- **S2** — `open_archive`에서 백그라운드 스레드로 전체 순차 추출. `archive::extract_all`(아카이브 1회 오픈, ZIP은 `by_index` 순회 / RAR는 `open_for_processing` 1패스)로 RAR의 페이지당 O(N) 재스캔(전체 O(N²))을 O(N)으로 낮춤.
- **S3** — `open_archive`마다 세대(generation) 증가 + 캐시 클리어, 백그라운드 스레드는 `insert_if_current`가 낡은 세대에서 `false`를 돌려주면 즉시 중단.
- 프런트·`Cache-Control: no-cache`·연속 뷰 lazy 로딩·PageView ±1 프리페치 모두 불변(Non-goals 준수). 메모리 상한 없음, 0→N 순서.
- 단위 테스트 5개 추가, 전체 27개 통과.

## 온스팟 결정 / 계획과의 차이
- **캐시를 Tauri와 분리한 별도 모듈(`page_cache.rs`)로 뺌** — 계획엔 모듈 분리를 명시 안 했으나, 이렇게 해야 S1(get/miss)·S3(세대 무효화)를 Tauri 하네스 없이 순수 단위 테스트로 검증 가능. 결과적으로 세 슬라이스 모두 실제 테스트를 획득.
- **리뷰에서 발견해 수정한 정합성 창(계획 밖 강화)** — 최초 구현은 세션(경로/페이지)을 먼저 갱신하고 캐시를 나중에 비웠음. 그 사이 짧은 창에서 프로토콜 요청이 옛 파일 캐시 바이트를 새 세션 컨텍스트로 서빙할 수 있어(실사용에선 프런트가 open 완료 후 요청하므로 발생 확률 낮음), **캐시 리셋을 세션 갱신보다 앞으로** 옮겨 원천 차단.

## 검증 상태 / 한계
- 동시성 자기 리뷰: 두 뮤텍스(ArchiveState·PageCache)를 **중첩 잠금하지 않음** → 데드락 없음. 세대 체크가 삽입과 같은 락 구간 안에서 원자적 → 전환 시 스테일 삽입 차단. 낡은 스레드는 다음 관심 페이지에서 중단 → 스레드 누적 없음.
- **S4(네트워크 드라이브 실제 체감)는 미완** — GUI·네트워크 드라이브가 필요해 기계 검증 불가. UAT로 사용자 확인 필요.
- clippy 미실행(툴체인에 미설치 — 프로젝트 관례).
